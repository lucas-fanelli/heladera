4. Arquitectura recomendada

PWA estática (Vite + React 19 + TypeScript + Motion) que habla directo con Firestore, servida por Firebase Hosting, con Auth anónima solo para que las reglas tengan un uid. No hay servidor propio, no hay API REST propia: el “backend” son las reglas de seguridad de Firestore. React y no Preact (cambio respecto de v1): el movimiento de la lista es requisito y se hace con Motion, que solo soporta React oficialmente; Preact vía preact/compat “anda” pero tiene una diferencia de timing de efectos que ya rompió exit animations en 2026 y ningún canal de soporte. Cuesta ~48 kB gz más; Motion pesa 34 y Firestore 100+; se precachea una vez. Si querés Preact igual, hay un spike de 30 min descrito en §13 (D12).

Dependencias, explícitas. La UI depende de dos abstracciones y nada más: una URL (“me abrieron en /l/<id>, quizás con ?anotar”) y una interfaz Db con 8 operaciones + suscribir. Detrás de Db hay tres implementaciones intercambiables: Firestore (producción), Node + SQLite (alternativa B) y una fake en memoria (tests y modo demo). Delante de la URL hay los accesos rápidos que quieras (ícono, link, QR, NFC, un atajo). Ni la pegatina ni Firebase se filtran a otra capa.

¿Por qué PWA y no una app nativa?

Una PWA es una web con un manifest (ícono, pantalla completa) y un service worker (caché para abrir sin señal); en Android Chrome se instala como un APK generado por Google y captura sus URLs; en iPhone es “sitio agregado al inicio”. Gana acá por: distribución = un link (sin Play Store USD 25 / App Store USD 99 al año + Mac, sin revisión, sin APKs de “fuentes desconocidas”), cero cuentas, un solo código para Android + iPhone + PC, $0 y sin plataforma que mantener, y porque todo lo que la lista necesita (tiempo real, offline, tildar, instalable) la web lo hace bien. Nativa gana en push confiable y sync en segundo plano (iOS no tiene background sync en web), en que el NFC abra la app y no Safari en iPhone, y en integración fina (widgets, Siri). Nada de eso está en el diseño. Si algún día hace falta, la misma app React se envuelve con Capacitor y va a las stores: es una implementación más del mismo contrato, no un rediseño.

Injertos de las otras propuestas

  • Link corto genérico (de C): https://<proyecto>.web.app/h redirige (301) a /l/<listId>. Sirve para la pegatina, para un QR impreso, para un favorito. Rotar el secreto = editar una línea de firebase.json, sin regrabar nada.
  • Cabeceras de Hosting (de B): Referrer-Policy: no-referrer (la URL es un secreto), Cache-Control: no-cache para index.html, sw.js y el manifest, y una CSP básica.
  • Semilla de sugerencias (de B): ~40 productos comunes (leche, yerba, pan, huevos, dulce de leche…) al crear la lista, para que el autocompletar no arranque vacío. Y aviso de duplicado antes de agregar.
  • Exportar JSON desde el menú, y un segundo Owner en el proyecto de Firebase (otro Gmail de confianza) para no perder la app si perdés la cuenta.

5. Modelo de datos y “API”

No hay endpoints propios: el contrato son paths de Firestore + reglas. Todo lo que el cliente puede hacer está en 8 operaciones del módulo db.

Documentos
listas/{listId}                 ← id aleatorio 20 chars (el secreto)
  nombre, creadaEn, esquema: 1

listas/{listId}/miembros/{memberId}
  nombre ("Mamá"), color, creadoEn
  · memberId ≠ uid: es "la persona", elegida en
    cada teléfono; 2 teléfonos = mismo memberId

listas/{listId}/items/{itemId}  ← id generado en cliente
  texto, textoNorm, estado: pendiente|comprado|borrado
  agregadoEn, agregadoPor (memberId), agregadoPorNombre
  compradoEn, compradoPor, compradoPorNombre
  borradoEn, actualizadoEn        ← todos serverTimestamp()

listas/{listId}/meta/sugerencias ← 1 doc, un mapa
  entradas: { textoNorm: { texto, veces, ultimaVez } }
Operaciones del módulo db
  1. crearLista(nombre, miembros[]) → batch: lista + miembros + sugerencias con semilla.
  2. elegirMiembro(memberId | nombreNuevo) → crea el miembro si no existe; guarda memberId en localStorage.
  3. agregarItem(texto) → set en items/{nuevoId} + increment en sugerencias (mismo batch).
  4. marcarComprado(itemId, bool) → update parcial de estado, compradoEn/Por.
  5. editarItem(itemId, texto) → update solo del texto (+ textoNorm).
  6. borrarItem(itemId) / deshacer → estado: borrado / vuelta a pendiente. Nunca deleteDoc.
  7. vaciarComprados() → batch de borrados lógicos (≤ 500).
  8. suscribir(listId, cb) → onSnapshot de ítems activos, miembros y sugerencias, con includeMetadataChanges para el puntito “pendiente de sincronizar”.

Decisiones de modelo que importan

  • Borrado lógico siempre. Si mamá tilda offline y papá borra online, dos updates se fusionan; un delete haría fallar la escritura encolada de mamá. Además hace trivial el “Deshacer”. Los borrados no se leen (la query filtra por estado) y crecen ~500 KB/año: irrelevante.
  • IDs de ítem generados en el cliente. “Agregar” es un set sobre un id fijo: reintentar nunca duplica.
  • Identidad por memberId, no por uid. El uid anónimo cambia entre Safari y la PWA instalada en iPhone; la persona no. Renombrar a “Mamá” actualiza un doc y la UI resuelve el nombre al pintar (join en cliente); agregadoPorNombre queda como respaldo.
  • Conflictos: última escritura gana por campo. Mamá marca comprado offline y papá edita el texto online → quedan los dos cambios. Los dos togglean el mismo ítem → gana el último en llegar. Caso raro “mamá compró / papá borró”: gana el último; si molesta, se separa en dos timestamps (compradoEn vs borradoEn) y se deriva el estado. No lo hago en v1. La tabla completa está en §6.
  • Deduplicación determinista. Si dos personas anotan lo mismo sin verse (mamá offline en el súper, papá en casa), llegan dos documentos con el mismo textoNorm. Cuando ambos ya están confirmados por el servidor (sin hasPendingWrites, timestamps finales), cualquier cliente que lo note conserva el más antiguo (por agregadoEn, desempate por id) y marca el otro como borrado. Todos aplican la misma regla → convergen; si dos la aplican a la vez es idempotente; como es borrado lógico, no se pierde nada. Toast: “Papá también anotó yogur; los junté”.
  • Normalización (textoNorm): minúsculas, sin tildes, espacios colapsados; la ñ se conserva (“ñoquis” ≠ “noquis”); emojis y signos se quitan; plural simple se iguala para el filtro pero no para la clave. Es la clave de duplicados, sugerencias y del incremento en Firestore: se escribe con FieldPath para que “coca 1.5 l” no se anide como coca → 1 → 5 l.
  • Sugerencias en un solo documento (mapa) → 1 lectura para tener todo el historial; el vocabulario de una casa son cientos de entradas contra un límite de ~8.000.
  • Sin índices compuestos: la query activa es where('estado','in',['pendiente','comprado']); el orden se hace en el cliente (<100 docs).
Reglas de seguridad (borrador exacto a desplegar) 
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function auth() { return request.auth != null; }
    function esStr(v, max) { return v is string && v.size() > 0 && v.size() <= max; }
    // las 11 claves de un ítem: exactamente esas (hasOnly + hasAll), así ningún cliente crea ítems a medias
    function clavesItem() { return ['texto','textoNorm','estado','agregadoEn','agregadoPor','agregadoPorNombre','compradoEn','compradoPor','compradoPorNombre','borradoEn','actualizadoEn']; }

    match /listas/{listId} {
      allow get: if auth();
      allow list: if false;                       // nadie enumera listas: la URL es la llave
      allow create: if auth()
        && request.resource.data.keys().hasOnly(['nombre','creadaEn','esquema'])
        && esStr(request.resource.data.nombre, 60);
      allow update: if auth()
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['nombre'])
        && esStr(request.resource.data.nombre, 60);
      allow delete: if false;

      match /miembros/{memberId} {
        allow read: if auth();
        allow create, update: if auth()
          && request.resource.data.keys().hasOnly(['nombre','color','creadoEn'])
          && esStr(request.resource.data.nombre, 30);
        allow delete: if false;
      }
      match /items/{itemId} {
        allow read: if auth();
        allow create: if auth()
          && request.resource.data.keys().hasOnly(clavesItem()) && request.resource.data.keys().hasAll(clavesItem())
          && esStr(request.resource.data.texto, 120)
          && request.resource.data.estado == 'pendiente';
        allow update: if auth()
          && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['agregadoPor','agregadoEn'])
          && esStr(request.resource.data.texto, 120)
          && request.resource.data.estado in ['pendiente','comprado','borrado'];
        allow delete: if false;
      }
      match /meta/sugerencias {
        allow read: if auth();
        allow create, update: if auth()
          && request.resource.data.keys().hasOnly(['entradas'])
          && request.resource.data.entradas.size() <= 5000;
        allow delete: if false;
      }
    }
  }
}

Las reglas no impiden que alguien con la URL escriba (es el modelo elegido); sí impiden basura sin forma, listados masivos y borrados físicos. Cambiar reglas = firebase deploy --only firestore:rules, sin redeploy de la app.

6. Tiempo real y offline

Tiempo real

Un listener onSnapshot por lista mantiene un stream abierto y recibe solo deltas. Papá agrega “cerveza” → en su pantalla aparece al instante (compensación de latencia local) → mamá lo ve en <0,5 s si tiene la app abierta. Costo: 1 lectura por documento cambiado por dispositivo que escucha. Un día muy activo: <300 lecturas contra 50.000 gratis por día.

Offline

Lectura: el service worker precachea el shell y la caché de Firestore tiene la última copia de la lista → la app abre y muestra todo sin señal (condición: haberla abierto online alguna vez en ese teléfono; el listener la mantiene fresca hasta el último segundo con señal). Escritura: cada acción se aplica a la caché y se encola; la cola sobrevive a cerrar la app y reiniciar el teléfono; al reconectar se manda en orden, exactamente una vez.

Límite que hay que decir en voz alta

No hay sincronización en segundo plano en la web (ni en iOS ni con la app cerrada). Si mamá tilda todo sin señal y no vuelve a abrir la app con conexión, papá no lo ve. Solución de producto: contador visible “3 cambios sin sincronizar” y el hábito natural de abrir la app al volver a casa. Es igual en las tres arquitecturas.

Quién “tiene razón” cuando dos escriben a la vez

Nadie: hay reglas de fusión deterministas y todos los teléfonos convergen al mismo estado. Modelo de consistencia eventual y convergente, sin bloqueos ni “alguien está editando”. Un documento por ítem; el servidor serializa las escrituras por documento; el orden es el de llegada al servidor, nunca el reloj del teléfono.

CasoQué pasa
Dos anotan cosas distintas a la vezSin conflicto: dos documentos con ids distintos (generados en el teléfono, 20 caracteres aleatorios; colisión imposible en la práctica).
Dos anotan lo mismo sin verse (offline, o en el mismo segundo)Dos documentos con el mismo textoNorm → deduplicación determinista (§5): se conserva el más antiguo, el otro pasa a borrado lógico; toast “Papá también anotó yogur; los junté”.
Dos tocan el mismo ítem, campos distintos (mamá tilda offline; papá corrige el texto online)Firestore fusiona por campo: quedan los dos cambios.
Dos tocan el mismo campo (los dos tildan/destildan el mismo ítem)Gana la última escritura en llegar al servidor. Nadie ve un error; el estado final es el mismo para todos. La verdad es lo que hay en el changuito.
Uno borra, otro tilda (sin verse)Como es borrado lógico, no falla ninguna escritura; gana la última en llegar. Si molesta, se deriva el estado de dos timestamps (§5).
Reintentos por señal malaNunca duplican: agregar es “escribir el documento con este id”; los reintentos del SDK son exactamente-una-vez.
Fechas y ordenSiempre serverTimestamp(): “hace 2 h” y el orden no dependen de que un teléfono tenga la hora mal. Mientras una escritura está pendiente, el SDK entrega una estimación y la UI la tolera (los ítems recién agregados van al final; no “saltan” al confirmarse).
La misma persona en dos teléfonosMismo memberId elegido en cada uno (“¿Sos vos, Mamá?”); dos uids anónimos distintos, una sola identidad.

Transacciones (leer-modificar-escribir con reintento) existen y no hacen falta: el único contador (sugerencias) usa increment atómico. En la alternativa Node sería igual, con un número de secuencia del servidor haciendo de orden.
