=== overTesting ===
- El SDK de Firebase en sí (que onSnapshot emite, que serverTimestamp se resuelve, que la cola offline persiste en IndexedDB): son garantías del proveedor. Testear TU uso (reglas, payloads, derivaciones), no el SDK.
- Snapshots visuales/píxel-perfect y tests de CSS (safe-area, tamaño de targets ≥44px, input ≥16px): son invariantes de diseño que se verifican una vez con Lighthouse/axe y una revisión manual en el celular; un test automático de eso es caro y frágil. Excepción barata: un lint estático de accesibilidad con axe en 1 E2E de humo.
- Cobertura exhaustiva de cada componente presentacional (chips, avatar de color, iconos): 3 usuarios, sin equipo; los tests de componente valen solo donde hay lógica (duplicados, delay, dialog, identidad).
- Mockear Firestore para tests de integración 'rápidos': el mock reproduce lo que vos creés que hace Firestore, no lo que hace; el emulador es el único mock aceptable. Si duele por Java, mejor menos tests pero reales.
- Web NFC, QR y Web Share end-to-end: no se pueden automatizar de forma confiable (hardware/permisos); solo unit de la lógica de detección/fallback y verificación manual en un Android real una vez.
- Tests de rendimiento/carga (miles de ítems, listas concurrentes): la lista de una familia tiene decenas de ítems; el único límite que importa (500 por batch, 5000 sugerencias) ya está en must-have.
- Test del redirect 301 en producción tras cada deploy como parte de la suite: un smoke manual post-deploy (abrir la pegatina) alcanza; automatizarlo contra prod requiere credenciales y da falsos negativos por propagación.
- La alternativa Node+SQLite+SSE, si llegara a ir: desaparecen los tests de reglas y el emulador (se reemplazan por tests de integración HTTP contra el server con SQLite en memoria, mucho más simples y sin Java), pero aparecen tests de reconexión de SSE (Last-Event-ID, reintento) y de la cola offline propia, que ya no la regala el SDK. No conviene testear ambas rutas: decidir primero.
